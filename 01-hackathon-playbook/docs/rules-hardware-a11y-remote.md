**Evidence status: read this first.** The sandbox blocked most sites, so almost nothing below is verified against a primary page. Only GitHub-hosted pages (MLH's standard rules, two Microsoft rules files, one Opportunity Hack issue) were read in full; they are marked **FETCHED**. Everything else is **SNIPPET-ONLY** (an AI-paraphrased search summary, not the page) or **UNVERIFIED** (background knowledge or unclear provenance). Do not quote SNIPPET-ONLY text as verbatim. Every vendor price and free-tier limit is **re-check before use**. Items labelled "our suggestion" or "inference" are the researchers' own syntheses, not organizer or industry standards. The notes contain no datathon-specific rules or sources, so every section applies to software hackathons only until someone adds datathon evidence (data licences, dataset terms, leaderboard rules).

The four gaps share one pattern: organizers mostly allow the new thing but punish silence about it. AI assistants are allowed if disclosed, pre-existing code is allowed if declared (and sometimes only if "meaningfully extended"), and demos are judged largely from a recorded video that must work without you. Judges also increasingly score accessibility, privacy and responsible AI, but at weights of roughly 5-30%, so it rarely decides a win and sometimes gates a prize. The hardware playbook has the thinnest evidence of the four: it rests on search snippets and low-authority blogs, so it is mostly our inference and should be labelled that way in the guide.

## 1. AI use, originality, pre-existing code and IP: allowed, but undisclosed use is what gets teams disqualified

### What is sourced

**AI assistants.** MLH's standard rules (**FETCHED**) say teams "may use AI to assist them while coding," including code completion, code generation and image generation, and should be "honest and transparent about the AI code tools they used," listing them in submissions and answering judge questions ([MLH standard rules](https://github.com/MLH/mlh-policies/blob/main/standard-hackathon-rules.md)). Disqualification is at organizers' discretion for rule-breaking or "unsporting behaviour". The same pattern appears in snippet-only summaries: MLH member-event guidelines reportedly require events to allow AI, say projects should be "created by humans," recommend a README separating what was built from what was used, warn against reskinning an existing AI tool, and send uncredited AI use to cheating@mlh.io ([MLH guidelines](https://github.com/MLH/mlh-policies/blob/main/member-event-guidelines.md), SNIPPET-ONLY). ETHGlobal reportedly permits ChatGPT, Claude Code, Copilot and Cursor but asks submissions to document which code, files or assets were AI-assisted, with disqualification, revoked prizes or bans for misrepresentation ([ETHGlobal rules](https://ethglobal.com/rules), SNIPPET-ONLY). Devpost-hosted events echo this: AWS "Agents for Humans" allows AI assistants and starter templates but requires disclosure of other pre-existing work ([rules](https://agentsforhumans.devpost.com/rules), SNIPPET-ONLY); USAII 2026 allows AI assistants if disclosed ([rules](https://usaii-global-ai-hackathon-2026.devpost.com/rules), SNIPPET-ONLY); First Commit 2026 reportedly treats non-disclosure as a violation ([repo](https://github.com/WaliMedugu/first-commit-hacathon-2026), SNIPPET-ONLY); ImpactHack 2026 reportedly penalises nothing about AI use ([page](https://impacthack26.devpost.com/), SNIPPET-ONLY). Microsoft Agents League 2026 (**FETCHED**) sets no AI-tool restriction but requires "your own original work" and a demo video "solely your own work" ([rules](https://github.com/microsoft/Agents-League-AISF-Regulations/blob/main/OFFICIAL%20RULES.md)). No source uses the phrase "vibe coding" in a rule.

**Pre-existing code.** MLH (**FETCHED**) lets teams pursue an earlier idea if they do not re-use code or project materials, allows libraries, frameworks and open source, and calls open-sourcing a project beforehand just to use it at the event "against the spirit of the rules" ([MLH](https://github.com/MLH/mlh-policies/blob/main/standard-hackathon-rules.md)). Microsoft AI Dev Days 2026 (**FETCHED**) requires projects to be "newly created" after the submission period opens, allows open source under licence compliance, and excludes projects developed with sponsor financial or preferential support ([rules](https://github.com/Azure/AI-Dev-Days-Hackathon/blob/main/OFFICIAL_RULES.md)). Snippet-only: ETHGlobal separates a "From Scratch" track from continuity tracks that allow existing code if documented, and pre-built entries cannot win partner prizes ([ETHGlobal](https://ethglobal.com/rules)); OpenAI Build Week and WebMCP accept pre-existing projects "meaningfully extended" after the start, judged only on the added work with documentation of prior versus new ([OpenAI](https://openai.devpost.com/rules), [WebMCP](https://webmcp.devpost.com/rules)).

**IP.** Entrants keep ownership; sponsors take a licence whose breadth varies. Microsoft AI Dev Days (**FETCHED**) requires the submission be "solely owned by you... with no other person or entity having any right or interest" and grants Microsoft a "worldwide, perpetual, irrevocable, royalty free" non-exclusive licence for promotion ([rules](https://github.com/Azure/AI-Dev-Days-Hackathon/blob/main/OFFICIAL_RULES.md)). Snippet-only: Google AI Hackathon asks for a perpetual, irrevocable licence including derivatives ([rules](https://googleai.devpost.com/rules)); Gemini 3, AWS Kiro and AWS AI Agent events say entrants keep IP, with a judging or narrower licence to the sponsor ([Gemini 3](https://gemini3.devpost.com/rules), [Kiro](https://kiro.devpost.com/rules), [AWS Agent](https://aws-agent-hackathon.devpost.com/rules)). MLH's standard rules (**FETCHED**) state no IP or sponsor-API terms.

### What is inference (ours)

Keep an AI log (tool, purpose, files) from hour one and put it in the README even when rules are silent. A thin LLM wrapper risks the "reskin" objection. Judges can inspect commit timestamps, so start a clean repo at kickoff and list templates and dependencies. A "solely owned" warranty can clash with copyleft dependencies, employer or university IP policies, and AI output of uncertain ownership. A broad perpetual licence means the sponsor may reuse anything in the repo or video. Sponsor-tech use is probably a prize condition (UNVERIFIED; no rules page read).

### Ready-to-use checklist

- Read the event's rules page for three things: AI policy, "from scratch" versus "extended" versus continuity, and licence grant. Where the rules are silent on AI, ask the organizers in writing.
- Start a fresh repo at kickoff; commit often so history shows work inside the window.
- Keep an AI log: tool and version, what it was used for, which files. (Our suggestion; see the card below.)
- List frameworks, libraries, templates, datasets and any pre-event code in the README with licences.
- If extending an existing project, write a "before vs after" section with evidence of new work.
- Confirm every teammate's employer or university permits entry and the licence grant; check copyleft conflicts with a "solely owned" clause.
- Make sure the project does more than reskin a hosted AI tool.
- Re-read the disqualification clause before submitting.

**AI use card (our own suggestion, not an organizer template):** tool and version; task it did; files or assets touched; what a human wrote, reviewed or tested; what was changed after review.

## 2. Hardware and IoT track: a thin sensor-to-dashboard slice with a fallback beats an ambitious build

### What is sourced

All of this is SNIPPET-ONLY. MLH member events may rent a hardware lab (Raspberry Pi 4B kits, Arduinos, Grove sensors, webcams, micro servos, motors and components); the number of labs is limited and reportedly sent to US-based events only ([MLH hardware](https://guide.mlh.io/general-information/event-logistics/hardware), [lab contents](https://guide.mlh.io/organizer-resources/hardware-lab-contents)). Lending rules such as deposits were not readable. StarkHacks at Purdue is billed as the largest hardware hackathon, with 750+ hackers and tracks including robotics, wearables and accessibility ([Purdue](https://engineering.purdue.edu/Engr/AboutUs/News/Spotlights/2026/2026-0519-purdue-starkhacks-hardware-hackathon)). Practitioner tips come from low-authority blogs: loose wires are the most common failure ("90% of the time"), hot-glue connections, pre-solder headers, bring power banks, pre-install the Pi OS and libraries, and avoid relying on venue Wi-Fi ([Zbotic](https://zbotic.in/how-to-win-a-hackathon-electronics-build-tips-for-students/), [Solaride](https://solaride.ee/blog/prepare-yourselves-how-to-survive-a-hardware-hackathon-aka-buildathon)). Backup advice is consistent across sources: run the demo roughly 20 times and keep a video ([Zbotic](https://zbotic.in/how-to-win-a-hackathon-electronics-build-tips-for-students/)), do 5-7 dry runs including offline ([Hack4Purpose](https://hack4purpose.in/hackathon-2025/)), and prepare a software-only fallback ([AngelHack](https://angelhack.com/blog/hackathon-best-practices/)). Reference builds exist as Hackster.io projects (none verified as hackathon winners), such as ESP32 gas detection over MQTT ([example](https://www.hackster.io/theembeddedthings/iot-projects-part-9-gas-detection-and-safety-monitoring-8de553)), an ESP32 4G GPS tracker that avoids venue Wi-Fi ([example](https://www.hackster.io/techgyanset/esp32-4g-lte-gps-tracker-with-mqtt-dashboard-19e738)), and TinyML gesture recognition on a Pico ([example](https://www.hackster.io/mjrobot/tinyml-motion-recognition-using-raspberry-pi-pico-6b6071)). The Wokwi simulator is listed as supported in Espressif's docs ([Espressif](https://docs.espressif.com/projects/arduino-esp32/en/latest/third_party/wokwi.html)).

**Free tiers (all SNIPPET-ONLY; re-check before use; Edge Impulse has revised its free plan, so its numbers may be dated).** Wokwi Community: unlimited simulations, 50 min/month free CI; paid Hobby EUR5.6/month ([pricing](https://wokwi.com/pricing)). Edge Impulse Developer plan: 60-minute training jobs ([pricing](https://www.edgeimpulse.com/pricing)). HiveMQ Cloud free: 100 connections, 10 GB/month, 3-day retention ([pricing](https://www.hivemq.com/pricing/)). EMQX Serverless free: 1M session minutes and 1 GB/month ([EMQX](https://www.emqx.com/en/blog/free-mqtt-broker)). Public test brokers exist but are not for sensitive data ([benchmark, 2022](https://goughlui.com/2022/10/23/project-benchmarking-public-free-mqtt-brokers/)).

### What is inference (ours)

Beginner defaults: ESP32 for Wi-Fi/BLE sensing, Raspberry Pi for camera, ML or a local broker, Arduino when the lab only stocks Uno-class boards. No source ranks platform popularity, and Pico and Jetson loaner availability is UNVERIFIED. A sensor-to-MQTT-to-live-dashboard story is likely the lowest-risk demo, and a local Pi broker or cellular link removes the venue Wi-Fi dependency. The time split for a 24-36 hour event (20% scope and parts check, 50% one end-to-end thin slice, last 20% freeze, backup video and rehearsal, plus a spare identically flashed board) is our suggestion, not sourced. No hardware-track judging criteria and no winner post-mortem were found.

### Ready-to-use checklist

- Before the event: ask which boards, sensors and tools are lent, and whether a deposit applies. Install the IDE, OS image and libraries offline.
- Pre-solder headers; bring a power bank, spare cables and a spare flashed board.
- Hour 1-4: hello-world on every board and sensor; decide the one core physical interaction.
- Build one end-to-end thin slice (sensor, transport, display) before polishing.
- Use a local broker or hotspot/cellular rather than venue Wi-Fi; do not push big downloads over event Wi-Fi.
- Prepare a simulator or recorded-data fallback (Wokwi or similar) and record a backup video as soon as the demo first works.
- Rehearse the full demo repeatedly, including with the network off. Re-check every vendor limit before relying on it.

## 3. Accessibility, privacy and responsible AI: cheap evidence covers most of what judges score

### What is sourced

All SNIPPET-ONLY. Several 2025-26 rubrics score these explicitly, with rubric text paraphrased, not verbatim. Resolve's Open Hackathon has an "Ethics, Security & Inclusion" category ([judging](https://resolvehackathon.open-conf.gr/judging-2025/)); Hack4SDG 2025 gives sustainability and ethics 20%, covering bias, privacy, accessibility and unintended consequences ([criteria](https://www.hack4sdg.com/2025-event/judging-criteria/)); Civic Hacks 2026 scores "Inclusion & Accessibility" and reportedly needs a minimum ethics score for best overall ([page](https://civic-hacks-2026.devpost.com/)); SANS AI Cybersecurity gives "Ethical & Responsible AI" 15% ([rules](https://ai-cybersecurity-hackathon.devpost.com/rules)); Impetus/AWS gives Responsible AI 5% ([Devpost](https://impetusawsgenaihackathon.devpost.com/)); Code For Change folds it into a 30% Social Good category ([Devpost](https://code-in-vision.devpost.com/)). MLH's four equal criteria (Technology, Design, Completion, Learning) contain no explicit ethics or accessibility item, though its community values call for accessible events ([MLH](https://mlh.io/community-values)).

On accessibility checks, WCAG 2.2 additions are summarised as: 24x24 CSS px minimum target size (2.5.8), focus not obscured (2.4.11), a non-drag alternative (2.5.7) and accessible authentication (3.3.8) ([Deque](https://dequeuniversity.com/resources/wcag-2.2/), [TetraLogical](https://tetralogical.com/blog/2023/10/05/whats-new-wcag-2.2/)). Lighthouse's score is a weighted average of axe-core audits ([Chrome docs](https://developer.chrome.com/docs/lighthouse/accessibility/scoring)); automated tools catch only part of the issues, with vendor and secondary claims ranging from 30-50% to about 57% (UNVERIFIED percentages) ([BOIA](https://www.boia.org/blog/googles-lighthouse-accessibility-tests-are-helpful-but-not-perfect), [Curb Cut](https://www.curbcutaccessibility.com/blog/lighthouse-accessibility-score-100/)). The classic criteria (4.5:1 text contrast, alt text, keyboard access, captions) come from background knowledge, not fetched this session; confirm at w3.org/WAI/WCAG22/quickref.

On privacy, GDPR Art. 5 requires data "adequate, relevant and limited to what is necessary" and limited retention ([GDPR Art. 5](https://gdpr-text.com/read/article-5/)). OpenAI's API reportedly does not train on API data by default, but that comes from third-party summaries, and consumer apps differ (UNVERIFIED; check each provider) ([OpenAI](https://developers.openai.com/api/docs/guides/your-data)). One event's rules allow modifying a submission after the deadline if it exposes personal data ([Qloo](https://qloo-hackathon.devpost.com/rules), SNIPPET-ONLY). NIST AI 600-1 (July 2024) lists 12 generative-AI risks including confabulation, data privacy, harmful bias and human-AI configuration ([summary](https://witness.ai/blog/nist-ai-600-1-generative-ai-profile/)); Model Cards have nine sections ([arXiv](https://arxiv.org/pdf/1810.03993)).

### What is inference (ours)

The 5-30% weights suggest these criteria usually break ties or gate prizes rather than decide a win. Under MLH's criteria, accessibility evidence could plausibly raise the Design score. The 15-minute accessibility check, the privacy minimum (synthetic or consented data, secrets out of the repo, say which provider receives user input) and the one-page AI Use Card below are **our own suggestions**, adapted from Model Cards and NIST, and are not an established standard. No judge interviews, provider retention pages or hackathon model-card requirements were found.

### Ready-to-use checklist

- Check the event rubric for ethics, accessibility or privacy weights and any minimum score.
- 15-minute accessibility pass (our suggestion): run axe, Lighthouse and WAVE on each demo screen; tab through the whole flow with no mouse; check contrast and no colour-only meaning; alt text, form labels, headings and page language; captions on the video, 200% zoom, phone width and reduced motion; note tested and untested areas in the README.
- Privacy minimum: no real personal, health, student or children's data in repo, video or prompts; `.env` ignored and secrets scanning run before going public; rotate any leaked key; name the AI provider and data sent; delete test data after judging.
- AI Use Card, one page (our suggestion): purpose and out-of-scope uses; models and versions; data sent and consent or synthetic status; failure modes with a spot-check result; bias check across two or three groups; where a human reviews or overrides; abuse cases; accessibility statement; open risks.

## 4. Remote logistics, team formation and demo reliability: the video and README are the submission

### What is sourced

The only primary-source evidence is **FETCHED**: Opportunity Hack's retrospective says live demos "eat too much time" and "exclude remote judges," so it will require recorded video demos from Fall 2026 ([issue #8](https://github.com/opportunity-hack/ops/issues/8)). Everything else is SNIPPET-ONLY. Video caps vary by event: about 3 min (OpenAI Build Week), under 3 (PayPal AI), about 4 (All Things Agentic), about 5 (ClimateHacks), so read each Rules page ([OpenAI](https://openai.devpost.com/updates/45282-openai-build-week-submissions-are-open-plugin-launch), [PayPal](https://paypalaihackathon.devpost.com/), [ClimateHacks](https://climatehacks.devpost.com/)). Devpost rules reportedly require a repo URL with spin-up instructions or a hosted demo, and private repos must be shared with testing@devpost.com and organizers ([Perplexity rules](https://perplexityhackathon.devpost.com/rules)); exact wording was not confirmed. Judges often watch the video first, then test the build ([Devpost judging help](https://help.devpost.com/hc/en-us/articles/360021798712-Online-judging-How-judging-works-for-judges)). Colosseum's recap advises a 2-3 minute video, an overview first, core features and stack, clear audio, and avoiding buzzwords and overruns ([Colosseum](https://blog.colosseum.com/perfecting-your-hackathon-submission/)); Devpost advice says show something working within about 90 seconds ([Devpost tips](https://info.devpost.com/blog/6-tips-for-making-a-hackathon-demo-video)), though page attribution was not confirmed.

For teams, practitioner posts (not research) recommend Discord team-formation channels, mixed roles, 3-5 people and written problem statements across time zones ([ServiceNow](https://www.servicenow.com/community/creatorcon-blogs/find-your-creatorcon-hackathon-teammates/ba-p/2910396), [WowDAO](https://www.linkedin.com/pulse/5-tips-form-a-list-team-worldwide-ai-hackathon-wowdaoai)). For reliability: record a backup video, test 10 minutes before and practise 10+ times ([Upstate Interactive](https://medium.com/upstate-interactive/8-tips-to-a-successful-hackathon-demo-and-presentation-4d1ae83415ad)); shared Wi-Fi degrades, so use wired or hotspots ([AngelHack](https://angelhack.com/blog/how-to-organize-a-hackathon/)); test API keys 24-48 hours ahead, cache responses and prefer simple key auth over OAuth ([APILayer](https://blog.apilayer.com/10-apis-that-will-make-your-hackathon-project-stand-out/), possibly paraphrased). No failure statistics were found. A "3-5 minutes per project" judging figure has unclear provenance (UNVERIFIED).

### What is inference (ours)

Because judging can be asynchronous, the video plus README or hosted link is effectively the whole submission. Suggested roles: builders for front end and back end, one demo owner who also presents, one submission owner for README, repo access and the form; a paragraph-long problem statement and a time-zone table in the team channel. Failure modes not sourced for hackathons (OAuth redirect URIs pointing at localhost, hosting cold starts, screen-share glitches, deploy breakage) are ordinary engineering reasoning, UNVERIFIED as hackathon evidence. **The 2:30 demo structure is our own suggestion, not an organizer template:** 0:00-0:20 problem and one-line solution; 0:20-1:50 live walkthrough of the core user path; 1:50-2:20 how it works; 2:20-2:30 impact and next step.

### Ready-to-use checklist

- Read the Rules page for video length, repo access, test credentials and submission fields.
- Join the event Discord early; post skills and a one-paragraph problem statement; aim for 3-5 people with mixed roles.
- Assign a demo owner and a submission owner; share private repos with named reviewer accounts before the deadline.
- Register production OAuth redirect URIs, test API keys 24-48 hours ahead, seed data, cache API responses and add an offline or mock mode.
- Freeze deploys before the deadline, pre-warm the server and keep a health-check page.
- Record the backup video when the demo first works; check audio and screen on export; keep it open in a tab.
- Rehearse screen sharing on the actual platform, use wired or hotspot internet, and test 10 minutes before presenting.

## Conclusion

The common thread is that organizer rules reward declared provenance and demonstrable reliability over novelty: an AI log, a pre-existing-work statement, an accessibility and AI Use Card, and a backup video are all cheap artefacts that map directly to disqualification clauses, rubric lines or judging mechanics. The guide can state these as practice, but should label sourcing honestly, since only MLH's standard rules, two Microsoft rules files and one organizer issue were read at source.

Before publishing, someone with open web access should close the biggest holes: read ETHGlobal, Devpost, MLH guide and WCAG pages directly; confirm all vendor limits; find a university-hackathon rules example; and research datathon-specific rules, which the notes do not cover. Until then, the hardware section and the 2:30 structure, AI Use Card and 15-minute accessibility check should be presented as our suggestions, not industry standards.
