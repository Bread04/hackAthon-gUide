## Twelve mechanics decide most LLM app designs

Builders do not need attention maths. They need the handful of mechanics that change cost, latency and reliability. The most important is billing. On the current Claude lineup, output tokens cost five times as much as input tokens. Thinking tokens are billed as output even when the thinking text is not returned to you ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing), [Thinking overview](https://platform.claude.com/docs/en/build-with-claude/thinking)). So **capping output and reasoning effort usually saves more money than trimming the prompt**. The second most important is position. In the "Lost in the Middle" study, accuracy on multi-document QA followed a U-shape: best when the relevant passage sat at the start or end of the context, worse in the middle (SNIPPET-ONLY, [arXiv 2307.03172](https://arxiv.org/abs/2307.03172)). Anthropic's own guidance agrees. It says to put long documents at the top and the query at the end, which "can improve response quality by up to 30 percent in tests" (vendor-reported, [prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). The third is that 2023-2024 tutorials are now partly wrong. On Opus 5.5, Sonnet 5.5, Fable 5.1 and related models, any non-default `temperature`, `top_p` or `top_k` returns a **400 error**, and Python SDK v1.0+ raises a `TypeError` if you pass them ([Thinking overview](https://platform.claude.com/docs/en/build-with-claude/thinking), [Opus 5.5 migration guide](https://platform.claude.com/docs/en/models/opus-5-5/migration-guide)). The docs we fetched record this behaviour but give no reason for it.

| Concept | What it is (plain) | Consequence for your app |
|---|---|---|
| **Tokens and tokenizers** | Models read and write sub-word tokens, and each model family splits text differently ([tiktoken](https://github.com/openai/tiktoken)). Claude 4.7+ uses a newer tokenizer that produces "approximately 30% more tokens for the same text"; the Opus 5.5 guide says "roughly 1x to 1.35x" ([pricing](https://platform.claude.com/docs/en/about-claude/pricing), [migration guide](https://platform.claude.com/docs/en/models/opus-5-5/migration-guide)) | Count tokens with the provider's [token-counting API](https://platform.claude.com/docs/en/build-with-claude/token-counting), not a characters/4 rule. Re-check your budget whenever you change model generation |
| **Context window** | Everything the model can see while it generates, including its own reply. The current Claude lineup has a 1M-token context and 128K max output ([models overview](https://platform.claude.com/docs/en/about-claude/models/overview)). 1M tokens is about 555k words on the new tokenizer | "It fits" does not mean "it works well". Retrieve or compact instead of dumping everything in. Anthropic calls server-side compaction "the primary strategy" for long agent runs ([context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)) |
| **Lost in the middle** | A U-shaped recall curve across GPT-3.5, GPT-4, Claude and open models (SNIPPET-ONLY, [arXiv 2307.03172](https://arxiv.org/abs/2307.03172)). Later replications reportedly find a smaller effect (UNVERIFIED) | Prompt order: documents first, question and key instructions last. For documents over 20k tokens, ask the model to quote the relevant passages first ([reduce hallucinations](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations)) |
| **Sampling knobs** | Temperature and top-p/top-k reshape the next-token distribution (UNVERIFIED background) | No "creativity slider" on current Claude models. Get consistency from schemas, examples and a demo cache. Local models (Ollama, llama.cpp) still expose the knobs |
| **System prompt** | A privileged instruction block before the conversation (UNVERIFIED background). It sits in the cached prefix: tools, then system, then messages ([prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)) | Keep it static: no timestamps or user IDs at the top, or every request misses the cache |
| **Tool-calling loop** | The model returns `stop_reason: "tool_use"`. Your code runs the tool and sends back a `tool_result` with the matching ID ([tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)) | An agent is a `while` loop that you own. Cap its iterations. Every turn resends the whole history, so cost grows with each step and caching matters |
| **Structured outputs** | `output_config.format` or `strict: true` tools guarantee schema-valid JSON. Not supported: recursive schemas, `minimum`/`maximum`, `minLength`/`maxLength`, most array constraints. Unsupported features return a 400 ([structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)) | Stop regex-parsing "reply in JSON". Keep schemas flat, and enforce numeric and length bounds yourself in Pydantic or Zod |
| **Prompt caching** | Reuses a processed prefix. 5-minute TTL by default (1 hour optional). Writes cost 1.25x base input (2x for 1h), reads 0.1x. Reads cost 5% on Opus 5.5 and 2.5% on Fable 5.1. Lookback is 20 blocks ([prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)) (re-check) | Order requests as tools → system → static documents → conversation. In long agent loops, add a second breakpoint so the 20-block lookback still finds a hit |
| **Streaming** | Server-sent events (`message_start`, `content_block_delta`, ...) carry text, tool input and thinking deltas ([streaming](https://platform.claude.com/docs/en/build-with-claude/streaming)) | Always stream in chat UIs, because time to first token is what users feel. Parse tool JSON only after its content block closes |
| **Embeddings vs generation** | An embedding model maps text to a vector, and a generation model writes text. Anthropic has no embedding model and points to Voyage 4 (32k context, 1024 dimensions by default) ([embeddings](https://platform.claude.com/docs/en/build-with-claude/embeddings)) | RAG needs two models. Choose the embedder once: changing it means re-embedding the whole corpus |
| **Hallucination** | Training and evaluation reward guessing over abstaining (SNIPPET-ONLY, [Kalai et al., OpenAI 2025](https://cdn.openai.com/pdf/d04913be-3f6f-4d2b-b283-ff432ef4aaa5/why-language-models-hallucinate.pdf)) | Give the model an explicit "not found" option. Require a citation per claim. Check prices, dates and API names with tools |
| **Reasoning / effort** | Thinking is adaptive and on by default on the 5.x models. `budget_tokens` is rejected on 4.7+. `effort` defaults to `high` on Sonnet 5.5 and Fable 5.1 and to `medium` on Opus 5.5 ([effort](https://platform.claude.com/docs/en/build-with-claude/effort), [models overview](https://platform.claude.com/docs/en/about-claude/models/overview)) | Lower effort for real-time or simple calls, raise it for multi-step tasks. Leave `max_tokens` headroom for thinking |
| **Cost and latency** | Per million tokens, input / output: Fable 5.1 $10 / $50, Opus 5.5 $4 / $20, Sonnet 5.5 $2 / $10, Haiku 4.5 $1 / $5. Batch API 50% off ([pricing](https://platform.claude.com/docs/en/about-claude/pricing)) (re-check) | Route easy or high-volume calls to cheaper models. Batch offline ingestion such as chunk contextualisation |
| **Local models** | llama.cpp runs quantized GGUF models with an OpenAI-compatible server ([llama.cpp](https://github.com/ggml-org/llama.cpp)). Ollama serves a REST API on `localhost:11434` ([ollama](https://github.com/ollama/ollama)). Ollama's OpenAI-compatible endpoint is UNVERIFIED | Free, private and offline for demos, at lower quality. If both sides speak the OpenAI-compatible API, switching between local and cloud is a base-URL change |

Put together, these give one prompt layout that serves caching and the U-shape at the same time: **tools, then a static system prompt, then long cached documents, then the changing conversation, with the question and key instructions last**. The research found no primary source for system-prompt internals. OpenAI and Gemini equivalents (structured outputs, reasoning effort, sampling restrictions) were not checked against primary docs.

## Learning resources split into builder track and internals track

For builders, the most useful repos are [anthropics/courses](https://github.com/anthropics/courses) and the [Claude cookbooks](https://github.com/anthropics/claude-cookbooks). The courses run in this order: API fundamentals, interactive prompting, real-world prompting, prompt evals, and tool use (including "Forcing JSON with tool use"). They use Claude 3 Haiku, so **model IDs and the temperature examples are dated** ([README](https://raw.githubusercontent.com/anthropics/courses/master/README.md)). The cookbooks cover RAG, Voyage embeddings, sub-agents (Haiku + Opus), prompt caching, JSON mode, evals and a cost-optimisation checklist. The old `anthropic-cookbook` path serves the same README, but a formal redirect was not confirmed ([README](https://raw.githubusercontent.com/anthropics/claude-cookbooks/main/README.md)). The [OpenAI cookbook](https://github.com/openai/openai-cookbook) (MIT) and [tiktoken](https://github.com/openai/tiktoken) are good for hands-on tokenization. For multi-agent design, read the [OpenAI Agents SDK orchestration doc](https://raw.githubusercontent.com/openai/openai-agents-python/main/docs/multi_agent.md), the [A2A repo and course](https://github.com/a2aproject/A2A), and the [MAST repo](https://github.com/multi-agent-systems-failure-taxonomy/MAST) with its annotated trace datasets. For RAG, use [RAG_Techniques](https://github.com/NirDiamant/RAG_Techniques) for learning only, because of its non-commercial licence, and the [chunking_evaluation](https://github.com/brandonstarxel/chunking_evaluation) code to test chunkers on your own data.

For "how it works inside", start with [rasbt/LLMs-from-scratch](https://github.com/rasbt/LLMs-from-scratch). It is the code for the Manning book and builds tokenization, attention, pretraining and finetuning step by step, with CI on three operating systems. [karpathy/nanochat](https://github.com/karpathy/nanochat) is the actively developed full-pipeline harness; its "time to GPT-2" leaderboard has entries from Jan-Mar 2026, down to 1.65 hours on 8xH100 ([README](https://raw.githubusercontent.com/karpathy/nanochat/master/README.md)). [mlabonne/llm-course](https://github.com/mlabonne/llm-course) is the broadest roadmap (Fundamentals / Scientist / Engineer, with quantization notebooks), and the [Hugging Face course](https://github.com/huggingface/course) covers Transformers. **Skip nanoGPT** (deprecated in favour of nanochat) and **LLM101n** (archived, "does not yet exist"). [llm.c](https://github.com/karpathy/llm.c) is pure C/CUDA pretraining and not app-oriented. Karpathy's "Intro to Large Language Models" is a talk, not a repo (UNVERIFIED in this session). A sensible weekend path is courses (API fundamentals → tool use), then the cookbook notebooks on caching, JSON and RAG, then optionally the first chapters of LLMs-from-scratch. Throughout, **prefer current platform docs over any notebook dated before 2026**, especially for sampling and thinking parameters. Star counts and last-push dates for these repos could not be collected.
