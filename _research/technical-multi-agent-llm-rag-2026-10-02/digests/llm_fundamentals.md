# LLM Fundamentals for Hackathon Builders (mechanics that drive app design, as of Oct 2026)

Research method note: Anthropic docs were fetched in full as markdown from platform.claude.com (`<page>.md`). GitHub READMEs were fetched from raw.githubusercontent.com. arXiv, the GitHub REST API and github.com HTML were all blocked in this sandbox, so the paper findings below come from search snippets only (marked SNIPPET-ONLY), and star counts could not be retrieved. Where an explanation is general background and no fetched source backs it, it is marked UNVERIFIED.

## For each concept: plain explanation + practical consequence for an app

### Takeaway
Most app-design decisions come from a few mechanics. You pay per token, and output tokens (thinking included) cost about 5x input. Models use information at the start and end of a long context better than information in the middle. Stable prefixes can be cached at roughly 10% of the input price. Tool calls and JSON are a client-side loop that you run. On current frontier Claude models, sampling knobs such as temperature are gone, and you steer behavior with prompts and an "effort" setting instead.

### Cited Findings

**1. Tokens and tokenization**
- Plain: models read and write tokens, not characters. A tokenizer (for example BPE) splits text into sub-word units, and different encodings split words, spaces and non-English text differently. Knowing a string's token count tells you (a) whether it fits the model and (b) what it costs. — [OpenAI cookbook: How to count tokens with tiktoken](https://github.com/openai/openai-cookbook/blob/main/examples/How_to_count_tokens_with_tiktoken.ipynb); [openai/tiktoken README](https://github.com/openai/tiktoken) ("fast BPE tokeniser"; `o200k_base` is used for gpt-4o and gpt-4o-mini, `cl100k_base` for gpt-4, gpt-3.5-turbo and text-embedding-3-*)
- Tokenizers change between model generations. Claude 4.7 and later models use a newer tokenizer that "produces approximately 30% more tokens for the same text", and the Opus 5.5 migration guide says it may use "roughly 1x to 1.35x as many tokens". — [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing); [Opus 5.5 migration guide](https://platform.claude.com/docs/en/models/opus-5-5/migration-guide)
- Rule of thumb from Anthropic: 1M tokens is about 555k words or 2.5M Unicode characters on the current tokenizer, while older models fit about 750k words in 1M tokens. 200k tokens is about 150k words. — [Models overview](https://platform.claude.com/docs/en/about-claude/models/overview)
- Anthropic has a token-counting API so you can check a message's size before sending it, for "rate limits and costs", "model routing decisions" and prompt length. — [Token counting](https://platform.claude.com/docs/en/build-with-claude/token-counting)
- App consequence: count tokens with the provider's own tokenizer or endpoint, not a character heuristic. Re-check budgets when you switch model generation, because the same text can cost up to about 35% more tokens.

**2. Context windows and "lost in the middle"**
- Plain: the context window is everything the model can reference when it generates, including its own response. It is the model's "working memory", separate from its training data. — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- Current Claude lineup (Fable 5.1, Opus 5.5, Sonnet 5.5): 1M-token context and 128K max output on the synchronous API. — [Models overview](https://platform.claude.com/docs/en/about-claude/models/overview)
- Lost in the Middle (Liu et al., 2023): across GPT-3.5, GPT-4, Claude and open models on multi-document QA, performance follows a U-shape. It is best when the relevant information is at the beginning or end of the context and worse when it sits in the middle. — SNIPPET-ONLY: [arXiv 2307.03172](https://arxiv.org/abs/2307.03172), [author PDF](https://cs.stanford.edu/~nfliu/papers/lost-in-the-middle.arxiv2023.pdf). A secondary summary claims later replications find the effect is smaller but still present (UNVERIFIED).
- Anthropic's guidance: "Place your long documents and inputs near the top of your prompt, above your query, instructions, and examples." "Queries at the end can improve response quality by up to 30 percent in tests, especially with complex, multidocument inputs." For long documents, ask the model to quote the relevant parts first. — [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Long contexts degrade, and Anthropic points to "context engineering" as the fix. For long conversations or agent runs, server-side compaction (summarizing earlier turns) is described as "the primary strategy for context management". Some models (Sonnet 5, Sonnet 4.6/4.5, Haiku 4.5) have "context awareness" of their remaining token budget. — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows); [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) (linked from that page, not fetched)
- App consequence: put the big documents first and the question and instructions last. Do not dump everything just because 1M tokens fit. Retrieve the relevant chunks (RAG) and compact or summarize long chats.

**3. Sampling (temperature / top-p / top-k) and why newer models restrict them**
- Plain (UNVERIFIED, general background): the model outputs a probability distribution over the next token. Temperature sharpens or flattens that distribution, and top-p/top-k cut it down to the most likely candidates before a token is sampled. Lower values give more deterministic output, higher values more varied output.
- Restriction: on Claude Fable 5.1, Mythos 5.1, Fable 5, Mythos 5, Mythos Preview, Opus 5.5, Opus 5, Opus 4.8, Opus 4.7, Sonnet 5.5 and Sonnet 5, any non-default `temperature`, `top_p` or `top_k` returns a 400 error on every request, with or without thinking. On older models the restriction applies only while thinking is on: `temperature` and `top_k` are incompatible with thinking, and `top_p` is allowed only between 0.95 and 1. — [Thinking overview, "Sampling parameters"](https://platform.claude.com/docs/en/build-with-claude/thinking)
- The migration guide says to "Omit `temperature`, `top_p`, and `top_k`... Use prompting to guide the model's behavior." Python SDK v1.0+ does not define these parameters, so passing them raises a `TypeError`. — [Opus 5.5 migration guide](https://platform.claude.com/docs/en/models/opus-5-5/migration-guide)
- Why: the fetched docs tie the restriction to thinking/reasoning models but do not explain the reason. Gap; see below.
- App consequence: do not build a "creativity slider" on temperature for current Claude models. Old tutorials that set `temperature=0` will break with a 400 or a TypeError. Get consistency from structured outputs, examples and prompts. Local and open models (Ollama, llama.cpp) still expose sampling knobs (UNVERIFIED for specific defaults).

**4. System prompts**
- Plain (UNVERIFIED, general background): the system prompt is a privileged instruction block that sits before the conversation and sets the role, rules and context for every turn.
- Mechanically, the system prompt is part of the cached prefix: "Cache prefixes are created in the following order: `tools`, `system`, then `messages`." — [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- App consequence: keep the system prompt static (no timestamps or per-user IDs at the top) so it caches. Put per-request data later in `messages`. Instructions that matter should come at the start (system) or end (final user turn), not buried in the middle of a long context (see the U-shape above).

**5. Tool / function calling loops**
- Plain: "Tool use (also called function calling) lets Claude call functions that you define or that Anthropic provides. Claude determines when to call a tool based on the user's request and the tool's description." For client tools, Claude replies with `stop_reason: "tool_use"` and one or more `tool_use` blocks. Your code runs the function and sends a `tool_result` block (with the matching `tool_use_id`) in a new request so Claude can continue. Server tools run on Anthropic's side. — [Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)
- Strict tool use (`strict: true`) guarantees schema-valid tool names and inputs. — [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- App consequence: an "agent" is a while-loop. Call the model, and if `stop_reason == "tool_use"`, execute the tools, append the results, and repeat until the model ends its turn. Cap the iterations. Write clear tool descriptions, since the model chooses tools from those descriptions. Every loop iteration resends the whole history, so cost grows with each step and caching matters.

**6. Structured outputs / JSON schema**
- Plain: structured outputs "constrain Claude's responses to follow a specific schema, ensuring valid, parseable output". There are two features: JSON outputs (`output_config.format`) and strict tool use (`strict: true`). — [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Supported: basic types, `enum` (primitives only), `const`, `anyOf`/`allOf` (limited), internal `$ref`/`$defs`, `required`, and `additionalProperties: false` (which is mandatory for objects). Common string formats (date-time, email, uri, uuid and others) work. Simple regex `pattern`s work.
- Not supported: recursive schemas, `minimum`/`maximum`/`multipleOf`, `minLength`/`maxLength`, array constraints beyond `minItems` 0 or 1, external `$ref`, backreferences, lookarounds and `\b`. An unsupported feature returns a 400 error. SDK helpers can transform schemas that use unsupported constraints. — [Structured outputs, JSON Schema limitations](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Learning resource: the anthropics/courses tool-use course has a lesson called "Forcing JSON with tool use". — [anthropics/courses tool_use](https://github.com/anthropics/courses/tree/master/tool_use)
- App consequence: use schema-constrained output (or strict tools) instead of "please reply in JSON" plus regex parsing. Keep schemas flat and simple. Enforce numeric and length bounds in your own validation code (for example Pydantic or Zod), because the API will not enforce them.

**7. Prompt caching**
- Plain: caching reuses already-processed prompt prefixes. It "significantly reduces processing time and costs for repetitive tasks". The cache stores the full prefix up to a `cache_control` breakpoint, and you can also turn on automatic caching. — [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Numbers: the default TTL is 5 minutes, refreshed for free on each use, and a 1-hour TTL is available. A 5-minute write costs 1.25x base input, a 1-hour write 2x, and a cache read 0.1x. Exceptions: reads cost 5% of base on Opus 5.5 and 2.5% on Fable 5.1 and Mythos 5.1. — [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching); [Models overview](https://platform.claude.com/docs/en/about-claude/models/overview)
- Gotchas: writes happen only at breakpoints. Reads look back at most 20 blocks for an earlier entry. A changing value such as a timestamp before the breakpoint means a fresh write and no hit on every request. The TTL is measured from the start of the request, so long streams eat into it. — [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- App consequence: order requests as tools, then system, then static documents, then the changing conversation. Put the breakpoint on the last stable block. In long agent loops, add a second breakpoint so the 20-block lookback still finds a hit.

**8. Streaming**
- Plain: with `"stream": true` the API sends the response incrementally as server-sent events (SSE). The event types are `message_start`, `content_block_start`, `content_block_delta`, `content_block_stop`, `message_delta`, `message_stop` and `ping`, and text, tool-use input and thinking all arrive as deltas. SDKs can also stream internally and return the complete Message. — [Streaming](https://platform.claude.com/docs/en/build-with-claude/streaming)
- The docs' examples stream when `max_tokens` is large (they use 128000), which points to streaming for long outputs. That it avoids HTTP timeouts is UNVERIFIED from the fetched text.
- App consequence: always stream in chat UIs, because time-to-first-token (TTFT) is what users perceive. Show a "thinking..." state while thinking or tool deltas arrive. Parse tool-use JSON only after its content block finishes.

**9. Embeddings vs generation models**
- Plain (partly UNVERIFIED background): an embedding model maps text to a fixed-length vector for similarity search. A generation model produces text. RAG uses embeddings to retrieve chunks, then passes them to the generator.
- "Anthropic does not offer its own embedding model." Its docs point to Voyage AI. The current Voyage 4 family (`voyage-4-large`, `voyage-4`, `voyage-4-lite`) has a 32,000-token context and 1024-dimension vectors by default (256, 512 and 2048 also available). The `-lite` model is "optimized for latency and cost". — [Embeddings](https://platform.claude.com/docs/en/build-with-claude/embeddings)
- OpenAI embedding models `text-embedding-3-small` and `text-embedding-3-large` use the `cl100k_base` encoding. — [tiktoken cookbook](https://github.com/openai/openai-cookbook/blob/main/examples/How_to_count_tokens_with_tiktoken.ipynb)
- App consequence: you need two models (or providers) for RAG. Pick the embedding model once, because changing it means re-embedding the whole corpus. Smaller dimensions mean cheaper storage and faster search.

**10. Hallucination: causes and mitigations**
- Cause (SNIPPET-ONLY): OpenAI's "Why Language Models Hallucinate" (Kalai, Nachum, Vempala, Zhang; Sept 2025) argues that models hallucinate because training and evaluation reward guessing over admitting uncertainty, like students bluffing on exams. It proposes changing benchmark scoring so that abstaining is not penalized. — [OpenAI PDF](https://cdn.openai.com/pdf/d04913be-3f6f-4d2b-b283-ff432ef4aaa5/why-language-models-hallucinate.pdf); [arXiv 2509.04664](https://arxiv.org/abs/2509.04664)
- Mitigations from Anthropic: let the model say "I don't know". For documents over 20k tokens, extract word-for-word quotes first and then answer only from those quotes. Have the model cite a quote for each claim and retract any claim it cannot support. — [Reduce hallucinations](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations)
- App consequence: ground answers in retrieved sources, show the citations in the UI, give the model an explicit "not found" option, and verify facts that matter (prices, dates, code APIs) with tools rather than trusting what the model remembers.

**11. Latency and cost drivers (input vs output tokens)**
- Pricing per million tokens (input / output): Fable 5.1 $10 / $50, Opus 5.5 $4 / $20, Sonnet 5.5 $2 / $10, Haiku 4.5 $1 / $5. Output costs 5x input across this lineup. The Batch API is 50% off. — [Pricing](https://platform.claude.com/docs/en/about-claude/pricing); [Models overview](https://platform.claude.com/docs/en/about-claude/models/overview)
- Relative latency: Fable 5.1 "Slower", Opus 5.5 "Moderate", Sonnet 5.5 "Fast". "Actual latency depends on prompt length, output length, and thinking effort." — [Models overview](https://platform.claude.com/docs/en/about-claude/models/overview)
- Latency guide: choose a faster model (it names Haiku 4.5), trim prompt and output tokens, and stream. It tracks baseline latency and TTFT. Its advice is to get the prompt working first and optimize latency afterwards. — [Reduce latency](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-latency)
- App consequence: limit output (`max_tokens`, "be concise") before you worry about input length. Cache large inputs. Route easy or high-volume calls to cheaper models. Use batch processing for offline jobs.

**12. Reasoning / extended-thinking models**
- Plain: the model produces reasoning tokens before its final answer. "The tokens Claude spends reasoning are billed as output tokens, even when the thinking text isn't returned to you, and they count toward `max_tokens`." What you see is "never the raw chain of thought" but a summary. — [Thinking overview](https://platform.claude.com/docs/en/build-with-claude/thinking)
- 2026 state: thinking is always on (adaptive) on Opus 5.5, Opus 5, Sonnet 5.5, Sonnet 5, Fable 5.1 and others, and `display` defaults to `"omitted"`. On Opus 4.6–4.8 and Sonnet 4.6 you opt in with `thinking: {type: "adaptive"}`. Manual `budget_tokens` mode is deprecated on 4.6 models and rejected with a 400 on 4.7 and later. — [Thinking overview](https://platform.claude.com/docs/en/build-with-claude/thinking); [Extended thinking](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)
- The `effort` parameter (`output_config.effort`) "lets you control how many tokens Claude spends", and it is the recommended thinking-depth control where adaptive thinking is available. Default effort is `high` on Fable 5.1 and Sonnet 5.5 and `medium` on Opus 5.5. — [Effort](https://platform.claude.com/docs/en/build-with-claude/effort); [Models overview](https://platform.claude.com/docs/en/about-claude/models/overview)
- App consequence: reasoning raises output-token cost and TTFT. Lower `effort` for simple or real-time calls and raise it for hard multi-step tasks. Leave enough `max_tokens` headroom for thinking.

**13. Small local models (Ollama, llama.cpp)**
- llama.cpp: "LLM inference in C/C++" with minimal setup. It supports 1.5- to 8-bit integer quantization "for faster inference and reduced memory use", Apple Silicon (Metal), CUDA, Vulkan and SYCL, and CPU+GPU hybrid inference for models larger than VRAM. It runs GGUF models from Hugging Face (`llama cli -hf ggml-org/Qwen3.5-0.8B-GGUF`) and has an OpenAI-compatible API server (`llama serve -hf ...`). — [ggml-org/llama.cpp README](https://github.com/ggml-org/llama.cpp)
- Ollama: one-line install on macOS, Linux and Windows, plus Docker. `ollama run gemma4` runs a model, there is a REST API at `http://localhost:11434/api/chat`, Python and JS libraries are available, and `ollama launch claude` sets up coding-tool integrations such as Claude Code and Codex. — [ollama/ollama README](https://github.com/ollama/ollama)
- Ollama also exposes an OpenAI-compatible endpoint (UNVERIFIED; the docs page could not be fetched).
- App consequence: local models give offline, free, private inference for demos, at lower quality and with hardware limits. Quantized 4-bit GGUF models are the usual laptop default (UNVERIFIED as a "default"). Because of OpenAI-compatible servers, you can switch between local and cloud models by changing the base URL.

### Inferences
- Order prompts so they satisfy caching and the U-shape at once: [tools] → [static system prompt] → [long docs, cached] → [dynamic conversation] → [the question and key instructions last].
- Because output costs 5x input and thinking is billed as output, controlling output and effort usually saves more money than shrinking the prompt.
- Tutorials from 2023–2024 (temperature=0, "JSON mode" via prompting, `budget_tokens`) are now partly obsolete for current Claude models. Builders should check the date of any guide they follow.

## Which GitHub-hosted educational resources best explain these?

### Takeaway
For app builders, the most useful resources are anthropics/courses (API fundamentals, prompting, evals, tool use) and the Claude and OpenAI cookbooks (caching, JSON, RAG, tool use, token counting). For a "how it works inside" understanding, the main options are rasbt/LLMs-from-scratch and karpathy/nanochat (nanoGPT is now deprecated in favor of nanochat). mlabonne/llm-course is the broadest roadmap. ### Inferences
- Suggested reading path for a hackathon: anthropics/courses (API fundamentals → tool use), then the cookbook notebooks for prompt caching, JSON and RAG, and optionally the first chapters of LLMs-from-scratch for intuition about tokenization and attention.
- Skip nanoGPT and LLM101n. One is deprecated and the other does not exist yet.
- Current docs (platform.claude.com) are more up to date than the course notebooks, especially on sampling parameters and thinking.
