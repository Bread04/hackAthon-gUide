# Build the simplest loop that wins

For a 24-48 hour hackathon the evidence points one way. **Start with one well-prompted model call, add retrieval only when the corpus will not fit in the prompt, and reach for multi-agent orchestration only for independent, read-only fan-out that you can show in a trace.** Three facts behind this matter more to a builder than how transformers work. You pay per token, and output (including hidden thinking) costs about **5x input**. Models use the start and end of a long prompt better than the middle. An "agent" is just a while-loop that you write around tool calls. Multi-agent systems cost about **15x the tokens of a chat** in Anthropic's measurements, and the MAST taxonomy shows they fail mostly through specification and coordination errors that engineering can fix, not through model weakness. In RAG, the best-documented gains still come from cheap upgrades to the naive pipeline (hybrid search, reranking, contextual chunk headers). GraphRAG, Self-RAG and CRAG are now in maintenance mode or dormant. Agentic retrieval loops inside general frameworks have taken their place. Hackathon winners we could verify use one coordinator with two or three named specialists, or a fixed state machine, plus Postgres or SQL memory and a mock mode that judges can reproduce. This report adds what the guide's existing pages (`agents-and-tool-use.md`, `rag-architecture.md`) lack: LLM mechanics, multi-agent communication and failure data, a RAG variant comparison, per-SDK reliability settings, named hackathon examples and learning resources. Versions come from PyPI on **2026-10-02**. Every price should be re-checked before you rely on it.

**Labels used throughout:** **SNIPPET-ONLY** means the finding comes from search-result summaries because the primary page (usually arXiv, ACL Anthology or a vendor blog) was blocked in the research sandbox. **UNVERIFIED** means general background or memory that no fetched source confirmed. **Vendor-reported** means a number published by the company or authors that sell or built the thing being measured. **(re-check)** marks a price.

## Twelve mechanics decide most LLM app designs

Builders do not need attention maths. They need the handful of mechanics that change cost, latency and reliability. The most important is billing. On the current Claude lineup, output tokens cost five times as much as input tokens. Thinking tokens are billed as output even when the thinking text is not returned to you ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing), [Thinking overview](https://platform.claude.com/docs/en/build-with-claude/thinking)). So **capping output and reasoning effort usually saves more money than trimming the prompt**. The second most important is position. In the "Lost in the Middle" study, accuracy on multi-document QA followed a U-shape: best when the relevant passage sat at the start or end of the context, worse in the middle (SNIPPET-ONLY, [arXiv 2307.03172](https://arxiv.org/abs/2307.03172)). Anthropic's own guidance agrees. It says to put long documents at the top and the query at the end, which "can improve response quality by up to 30 percent in tests" (vendor-reported, [prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). The third is that 2023-2024 tutorials are now partly wrong. On Opus 5.5, Sonnet 5.5, Fable 5.1 and related models, any non-default `temperature`, `top_p` or `top_k` returns a **400 error**, and Python SDK v1.0+ raises a `TypeError` if you pass them ([Thinking overview](https://platform.claude.com/docs/en/build-with-claude/thinking), [Opus 5.5 migration guide](https://platform.claude.com/docs/en/models/opus-5-5/migration-guide)). The docs we fetched record this behaviour but give no reason for it.

## Multi-agent systems buy tokens, not intelligence

### One pattern ladder, two orchestration primitives

Anthropic, OpenAI and the main frameworks agree on the order in which to add complexity. The guide's agents page already has the seven-rung ladder. What it lacks is the evidence for the top rung. Anthropic's production research system is **orchestrator-worker**. A LeadResearcher saves its plan to external memory, because context over 200,000 tokens gets truncated. It spawns parallel subagents that each have their own context window, and a separate CitationAgent then attributes claims to sources. With Opus 4 as lead and Sonnet 4 subagents, it "outperformed single-agent Claude Opus 4 by **90.2%**" on an internal research eval (vendor-reported, [Anthropic](https://www.anthropic.com/engineering/built-multi-agent-research-system)). The same post explains the gain. "Multi-agent systems work mainly because they help spend enough tokens to solve the problem": on BrowseComp, **token usage alone explained 80% of performance variance**. So before you credit the architecture, compare it with a single agent given the same token budget. Anthropic also encodes effort-scaling rules in the lead prompt: 1 agent with 3-10 tool calls for fact-finding, 2-4 subagents with 10-15 calls each for comparisons, and more than 10 subagents only for complex research. Each delegation brief carries "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries" ([Anthropic](https://www.anthropic.com/engineering/built-multi-agent-research-system)).

OpenAI's Agents SDK reduces the design space to two primitives that can be combined. With **agents as tools**, "a manager agent keeps control of the conversation and calls specialist agents through `Agent.as_tool()`". With **handoffs**, a triage agent routes to a specialist that "becomes the active agent for the rest of the turn". The docs add that orchestrating in code is "more deterministic and predictable, in terms of speed, cost and performance" than letting the LLM decide ([OpenAI Agents SDK docs](https://raw.githubusercontent.com/openai/openai-agents-python/main/docs/multi_agent.md)). The other frameworks name the same split differently. LangGraph has a **supervisor** and a **swarm**, and LangChain now recommends "using the supervisor pattern directly via tools rather than this library for most use cases" ([langgraph-supervisor-py](https://raw.githubusercontent.com/langchain-ai/langgraph-supervisor-py/main/README.md), [langgraph-swarm-py](https://raw.githubusercontent.com/langchain-ai/langgraph-swarm-py/main/README.md)). CrewAI splits "Crews" (autonomy) from "Flows" (event-driven control) ([crewAI](https://raw.githubusercontent.com/crewAIInc/crewAI/main/README.md)). Microsoft Agent Framework offers "sequential, concurrent, handoff, and group collaboration patterns" ([agent-framework](https://raw.githubusercontent.com/microsoft/agent-framework/main/README.md)). **Agents-as-tools, supervisor-via-tools, lead-spawns-subagents and Claude Agent SDK subagents are the same pattern**, and it is the default in 2026. Handoff/swarm fits conversational triage such as customer support. Supervisor fits work whose outputs must be merged into one answer. Two further patterns are named in the literature but were not verified here. Multi-agent **debate** (Du et al., arXiv 2305.14325) is UNVERIFIED. A **blackboard** design, where agents share a state store, is UNVERIFIED as a named pattern; its closest confirmed analogues are LangGraph's shared graph state and Anthropic's artifact pattern below. Cognition's "Don't Build Multi-Agents" argues for sharing full agent traces, not just messages, because "actions carry implicit decisions". A reported April 2026 follow-up says a narrow class of setups does work (SNIPPET-ONLY, [summary](https://fortegrp.com/insights/designing-effective-agent-architectures-principles-for-enterprise-ai-systems), [X post](https://x.com/walden_yan/status/2047054401341370639)).

### Communication: pass references in-process, use MCP for tools and A2A across boundaries

Inside one app, agents communicate in three ways. A subagent can be called as a tool and return its result to the caller. Control can be handed off. Or agents can share a state or memory store. Anthropic's lesson from production is to **pass references, not payloads**: "Subagents call tools to store their work in external systems, then pass lightweight references back to the coordinator". This avoids a "game of telephone" and cuts the token cost of copying large outputs through the conversation history. Their coordination is synchronous, which has a cost. "The lead agent can't steer subagents, subagents can't coordinate, and the entire system can be blocked while waiting for a single subagent." Going asynchronous would add "challenges in result coordination, state consistency, and error propagation" ([Anthropic](https://www.anthropic.com/engineering/built-multi-agent-research-system)). Two protocols cover the boundaries. **MCP** standardises agent-to-tool and agent-to-data connections, and the guide's agents page covers the 2026-07-28 spec. The Python SDK `mcp` is at **2.2.0** (2026-09-07, [PyPI](https://pypi.org/pypi/mcp/json)). Tool descriptions are a measured performance lever: a tool-testing agent that rewrote MCP tool descriptions cut task completion time by **40%** (vendor-reported, [Anthropic](https://www.anthropic.com/engineering/built-multi-agent-research-system)). **A2A (Agent2Agent)** is for peers. It is a Linux Foundation project, contributed by Google, for "communication and interoperability between opaque agentic applications". It uses capability discovery through **Agent Cards** and JSON-RPC 2.0 over HTTP(S) with sync, SSE streaming and push notifications, and agents collaborate "without exposing their internal state, memory, or tools". It describes itself as complementing MCP. `a2a-sdk` is at **1.2.1** (2026-09-30) ([A2A README](https://raw.githubusercontent.com/a2aproject/A2A/main/README.md), [PyPI](https://pypi.org/pypi/a2a-sdk/json)). Microsoft Agent Framework advertises A2A and MCP interop, and Google ADK 2.x has a Task API for agent-to-agent delegation ([autogen README](https://raw.githubusercontent.com/microsoft/autogen/main/README.md), [adk-python](https://raw.githubusercontent.com/google/adk-python/main/README.md)). **A2A only earns its place when agents cross process or organisation boundaries. Inside a hackathon app, a function call is simpler.** The claim that MCP was donated to the Linux Foundation's Agentic AI Foundation in December 2025 is UNVERIFIED.

### Failure modes: MAST says specification breaks first

Multi-agent costs are steep and documented. "Agents typically use about **4× more tokens** than chat interactions, and multi-agent systems use about **15× more tokens** than chats", which is roughly 3.75x a single agent. Anthropic concludes that such systems "require tasks where the value of the task is high enough to pay for the increased performance" (vendor-reported, [Anthropic](https://www.anthropic.com/engineering/built-multi-agent-research-system)). Its early failures are a useful checklist for a hackathon team: "spawning 50 subagents for simple queries", "scouring the web endlessly for nonexistent sources", agents "distracting each other with excessive updates", duplicated work caused by vague delegation, and a preference for "SEO-optimized content farms" over authoritative sources. Because "small changes to the lead agent can unpredictably change how subagents behave", the fixes are checkpoints, retries, full tracing and explicit effort budgets ([Anthropic](https://www.anthropic.com/engineering/built-multi-agent-research-system)).

The academic taxonomy is **MAST**, from "Why Do Multi-Agent LLM Systems Fail?" (Cemri, Pan, Yang et al., UC Berkeley; NeurIPS 2025 Datasets & Benchmarks). It defines **14 failure modes in three categories**, built from 150 expert-annotated traces with inter-annotator κ = 0.88, and the MAST-Data set has more than 1,600 annotated traces from 7 frameworks ([MAST repo](https://raw.githubusercontent.com/multi-agent-systems-failure-taxonomy/MAST/main/README.md), [NeurIPS PDF](https://proceedings.neurips.cc/paper_files/paper/2025/file/b1041e52d3be19f0a9bc491657488e4a-Paper-Datasets_and_Benchmarks_Track.pdf); counts are SNIPPET-ONLY, [arXiv 2503.13657](https://arxiv.org/html/2503.13657v3)). Paper versions differ in their counts: one snippet says "five open-source frameworks across 150 tasks", and the repo says "over 1K annotated MAS traces". A GitHub issue notes that the human-labelled data "spans three taxonomy versions with renumbered codes" ([issue #18](https://github.com/multi-agent-systems-failure-taxonomy/MAST/issues/18)), so **mode numbers below may not match every paper version**. A secondary aggregator reports category shares of about **41.8% specification, 36.9% inter-agent misalignment and 21.3% verification** (SNIPPET-ONLY, [futureagi](https://futureagi.substack.com/p/why-do-multi-agent-llm-systems-fail)).

| MAST category | Failure modes (SNIPPET-ONLY unless marked) | Hackathon countermeasure |
|---|---|---|
| **FC1 Specification / system design** | FM-1.1 Disobey task spec (≈11.8% per snippet), FM-1.2 Disobey role spec (UNVERIFIED), FM-1.3 Step repetition (among the most common), FM-1.4 Loss of conversation history, FM-1.5 Unaware of termination conditions | Write an explicit role, output format and stop rule per agent. Hard iteration cap. Persist the plan outside the context window |
| **FC2 Inter-agent misalignment** | FM-2.1 Conversation reset, FM-2.2 Fail to ask for clarification (UNVERIFIED), FM-2.3 Task derailment (UNVERIFIED), FM-2.4 Information withholding, FM-2.5 Ignored other agent's input, FM-2.6 Reasoning-action mismatch | Fewer agents. Pass artifact references, not paraphrases. Give coordinators the full subagent output or trace |
| **FC3 Task verification / termination** | FM-3.1 Premature termination, FM-3.2 No or incomplete verification, FM-3.3 Incorrect verification (UNVERIFIED) | Add an independent verifier or evaluator-optimizer step, and assert outcomes in golden fixtures |

Snippets say "unaware of termination conditions" and "information withholding" appear "almost exclusively in failed runs" ([HF IBM/Berkeley blog](https://huggingface.co/blog/ibm-research/itbenchandmast), SNIPPET-ONLY), and that failures stem from "system design decisions and poor or ambiguous prompt specifications" ([arXiv PDF](https://arxiv.org/pdf/2503.13657), SNIPPET-ONLY). The practical reading is that **most MAST categories respond to engineering**: specs, caps and verifiers. A single agent or a fixed workflow wins when subtasks share context or depend on each other heavily ("most coding tasks involve fewer truly parallelizable tasks than research"), when the task is not worth 15x the tokens, or when one context window is enough ([Anthropic](https://www.anthropic.com/engineering/built-multi-agent-research-system)). Apart from Anthropic's multipliers, the research found no independent benchmark of single-agent versus multi-agent cost.

## Most RAG variants lose to three cheap upgrades

The guide's `rag-architecture.md` already prescribes contextual retrieval, hybrid search and reranking in Supabase. What it lacks is a view of the alternatives, with honest evidence grades. The rough order of value per hour of hackathon work is: **long context (if the corpus is small) > naive RAG > hybrid + rerank > contextual retrieval > agentic loop > parent-child > query rewriting > CRAG-style grading > LightRAG > ColPali > GraphRAG > Self-RAG training**. That ranking is an inference from the evidence below, not a measured result. One discrepancy needs flagging. The guide's default chunk size is about 800 tokens, following Anthropic. Chroma's chunking report found RecursiveCharacterTextSplitter at **200 tokens with no overlap** "performed consistently well across all metrics", with 85.4-89.5% recall, while LLMSemanticChunker reached 91.9% recall (SNIPPET-ONLY, [Chroma research](https://www.trychroma.com/research/evaluating-chunking); code at [chunking_evaluation](https://github.com/brandonstarxel/chunking_evaluation)). The two sources measured different things, so treat chunk size as a parameter to test on your golden set rather than a settled default.

In LightRAG's LLM-judged tests HyDE won only 24.8% against LightRAG, near NaiveRAG (vendor-reported, [LightRAG](https://github.com/HKUDS/LightRAG)) | Multi-query for vague chat turns; HyDE is low priority |
| **CRAG / Self-RAG** | CRAG: an evaluator grades retrieved docs and falls back to web search. Self-RAG: a fine-tuned LM emits reflection tokens | Self-RAG needs training; CRAG-style grading is +1 call | [Self-RAG](https://github.com/AkariAsai/self-rag) (ICLR 2024); [CRAG](https://github.com/HuskyInSalt/CRAG) ([arXiv 2401.15884](https://arxiv.org/pdf/2401.15884.pdf)) | Don't train. Re-create the grade → rewrite → web-fallback loop in LangGraph as a "self-correcting" demo story |
| **LightRAG** | Knowledge graph plus vectors, dual-level retrieval, incremental updates | pip install with a web UI; default stores "not for production", Postgres recommended | Overall win rates vs NaiveRAG 60.0-84.8%, roughly even with GraphRAG (49.6-54.8%); self-reported LLM pairwise judgments, not accuracy ([LightRAG](https://github.com/HKUDS/LightRAG)) | Best graph option if cross-document entities matter to the demo |
| **GraphRAG (Microsoft)** | LLM-extracted knowledge graph, Leiden communities, pre-summarised; global map-reduce or local fan-out | "Indexing can be an expensive operation… start small" ([graphrag](https://github.com/microsoft/graphrag)) | 72-83% comprehensiveness win rate on global sensemaking over ~1M-token datasets; root summaries used 9-43x fewer tokens per query (SNIPPET-ONLY, LLM-judged, [arXiv 2404.16130](https://arxiv.org/abs/2404.16130)) | Only for "summarise themes across the whole corpus"; now frozen |
| **Multimodal (ColPali)** | A VLM embeds page images into ColBERT-style multi-vectors; no OCR step | Needs a GPU and a multi-vector store (store support UNVERIFIED); ~256KB per page | ViDoRe nDCG@5 81.3 vs 67.0 for the best OCR pipeline; >10x faster indexing (SNIPPET-ONLY, [ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/file/99e9e141aafc314f76b0ca3dd66898b3-Paper-Conference.pdf)) | Worth it for slides and scanned or chart-heavy PDFs; [RAGFlow](https://github.com/infiniflow/ragflow) is the parsing alternative |

Two cautions follow. The graph approaches are scored with **LLM pairwise "comprehensiveness/diversity" win rates**, not exact-match accuracy, so their benefit is broad summarisation, not factoid lookup. And the projects that maintain the variants tell the same story as the evidence: research pipelines are freezing while agentic loops in general frameworks take over.

## Ship a fixed pipeline with a mock mode and one visible handoff

### Decision tree

The decision tree below combines Anthropic's escalation advice ("optimizing single LLM calls with retrieval and in-context examples is usually enough", [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)), the long-context evidence above, and what verified winners actually built. Its "when not to" branches matter as much as its "do" branches.

```text
Does the demo need the model to take actions or choose among tools at runtime?
├─ No → Is the source corpus < ~200k tokens (a few docs)?
│        ├─ Yes → ONE CALL + cached long context. No RAG. Stop here.
│        └─ No  → RAG: naive → hybrid + rerank → contextual chunks (guide pipeline).
│                 Visual PDFs/slides? → ColPali or RAGFlow parsing.
│                 "Themes across whole corpus" is THE demo? → LightRAG (not GraphRAG).
└─ Yes → Can you draw the steps on a whiteboard in advance?
         ├─ Yes → FIXED WORKFLOW / state machine (chain, router, evaluator loop).
         │        Retrieval needed mid-flow? → retrieval as one node.
         └─ No  → SINGLE AGENT with ≤ ~10 tools and an explicit step cap.
                  Multi-hop questions over docs? → agentic RAG (search as a tool).
                  Is there independent, read-only fan-out (parallel research,
                  per-source analysis) AND the task is worth ~15x chat tokens?
                  ├─ Yes → ORCHESTRATOR + 2-4 SUBAGENTS as tools, artifacts by reference,
                  │        each with objective / output format / tools / boundaries.
                  └─ No  → stay single-agent. Do NOT split shared-context work
                           (e.g. one codebase) across agents.
Crossing a process/org boundary between agents? → only then consider A2A.
```

Agent-focused rubrics now reward evidence of reliability over the "multi-agent" label. One participant's transcription of the Multi-App AI Agent Hackathon (Sept 2026) brief weights **30% technical execution** ("actions, not just reads"), **25% reliability & evaluation** ("Retries, failure modes, traces, evals"), 20% usefulness, 15% originality and 10% demo clarity, and states "Not: a chatbot that only talks" ([Life OS Hackathon.md](https://raw.githubusercontent.com/SaurabhVelankar/multi-app-ai-agent-hackathon/main/Hackathon.md); the official site was blocked). Microsoft's AI Agents Hackathon 2025 judged "innovation, impact, usability, solution quality, and category alignment", and "multi-agent" was not a criterion in itself ([winners.md](https://raw.githubusercontent.com/microsoft/AI_Agents_Hackathon/main/docs/winners.md)). AngelHack's 2026 playbook reportedly tells judges to evaluate "task completion rate, tool-use accuracy, cost per run, and latency", and warns that otherwise "judges score videos and vibes" (SNIPPET-ONLY, [AngelHack](https://angelhack.com/blog/ai-agent-hackathon/)). **Claim "multi-agent" only if each agent has a distinct role you can show in a trace or UI.**

### Reliability settings per SDK

**The defaults vary enormously, so set every cap yourself.** LangGraph's current default recursion limit is **10,007 steps**, read from `LANGGRAPH_DEFAULT_RECURSION_LIMIT` ([_config.py](https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/langgraph/langgraph/_internal/_config.py)). Older versions defaulted to 25 (UNVERIFIED). In practice, the LangGraph default does not stop a runaway loop.

| SDK | Step cap | Graceful fallback | Other controls | Tracing |
|---|---|---|---|---|
| OpenAI Agents SDK | `max_turns`; exceeding it raises `MaxTurnsExceeded` (the guide records a default of 10) | `Runner` `error_handlers` keyed by `"max_turns"`, `"model_refusal"` and `"invalid_final_output"` return "a controlled final output" ([running_agents.md](https://raw.githubusercontent.com/openai/openai-agents-python/main/docs/running_agents.md)) | Guardrails, human-in-the-loop, sessions | Built in ([README](https://github.com/openai/openai-agents-python)) |
| LangGraph | `recursion_limit` in config; **default 10007** | Catch `GraphRecursionError` ("prevents infinite loops", [errors.py](https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/langgraph/langgraph/errors.py)) | Checkpointing, human-in-the-loop interrupts | LangSmith (agent-chat-ui asks for a key on deployed servers) |
| CrewAI | Per-agent `max_iter` | — | `max_rpm` rate cap; tool-result caching with crew `cache=True` ([base_agent.py](https://raw.githubusercontent.com/crewAIInc/crewAI/main/lib/crewai/src/crewai/agents/agent_builder/base_agent.py)) | — |

The guide's agents page lists Phoenix under ELv2 in `evidence.md`, so do not call it "OSI open source". The guide already covers caps for the AI SDK and the Anthropic tool runner. Building on those, the most transferable reliability pattern comes from Life OS, a roughly 6.5-hour one-day build. Its connectors use "a deterministic **sandbox** (`LIFE_OS_USE_MOCK_CONNECTORS=1`) so judges can reproduce without OAuth". Its evals are **four golden JSON fixtures** (meeting email, simple goal, ambiguous email, newsletter), run through the real graph in mock mode. Each fixture asserts which apps were written, whether human-in-the-loop triggered, and that an audit row exists, with the LLM mocked entirely ([Life OS README](https://github.com/SaurabhVelankar/multi-app-ai-agent-hackathon), [EVALS.md](https://raw.githubusercontent.com/SaurabhVelankar/multi-app-ai-agent-hackathon/main/EVALS.md)). For RAG, the analogue is a 20-50 question golden set with gold chunks, modelled on Anthropic's `evaluation_set.jsonl` ([claude-cookbooks](https://github.com/anthropics/claude-cookbooks/tree/main/capabilities/contextual-embeddings)) and scored with DeepEval's pytest-style metrics ([deepeval](https://github.com/confident-ai/deepeval)).

## Learning resources split into builder track and internals track

For builders, the most useful repos are [anthropics/courses](https://github.com/anthropics/courses) and the [Claude cookbooks](https://github.com/anthropics/claude-cookbooks). The courses run in this order: API fundamentals, interactive prompting, real-world prompting, prompt evals, and tool use (including "Forcing JSON with tool use"). They use Claude 3 Haiku, so **model IDs and the temperature examples are dated** ([README](https://raw.githubusercontent.com/anthropics/courses/master/README.md)). The cookbooks cover RAG, Voyage embeddings, sub-agents (Haiku + Opus), prompt caching, JSON mode, evals and a cost-optimisation checklist. The old `anthropic-cookbook` path serves the same README, but a formal redirect was not confirmed ([README](https://raw.githubusercontent.com/anthropics/claude-cookbooks/main/README.md)). The [OpenAI cookbook](https://github.com/openai/openai-cookbook) (MIT) and [tiktoken](https://github.com/openai/tiktoken) are good for hands-on tokenization. For multi-agent design, read the [OpenAI Agents SDK orchestration doc](https://raw.githubusercontent.com/openai/openai-agents-python/main/docs/multi_agent.md), the [A2A repo and course](https://github.com/a2aproject/A2A), and the [MAST repo](https://github.com/multi-agent-systems-failure-taxonomy/MAST) with its annotated trace datasets. For RAG, use [RAG_Techniques](https://github.com/NirDiamant/RAG_Techniques) for learning only, because of its non-commercial licence, and the [chunking_evaluation](https://github.com/brandonstarxel/chunking_evaluation) code to test chunkers on your own data.

For "how it works inside", start with [rasbt/LLMs-from-scratch](https://github.com/rasbt/LLMs-from-scratch). It is the code for the Manning book and builds tokenization, attention, pretraining and finetuning step by step, with CI on three operating systems. [karpathy/nanochat](https://github.com/karpathy/nanochat) is the actively developed full-pipeline harness; its "time to GPT-2" leaderboard has entries from Jan-Mar 2026, down to 1.65 hours on 8xH100 ([README](https://raw.githubusercontent.com/karpathy/nanochat/master/README.md)). [mlabonne/llm-course](https://github.com/mlabonne/llm-course) is the broadest roadmap (Fundamentals / Scientist / Engineer, with quantization notebooks), and the [Hugging Face course](https://github.com/huggingface/course) covers Transformers. **Skip nanoGPT** (deprecated in favour of nanochat) and **LLM101n** (archived, "does not yet exist"). [llm.c](https://github.com/karpathy/llm.c) is pure C/CUDA pretraining and not app-oriented. Karpathy's "Intro to Large Language Models" is a talk, not a repo (UNVERIFIED in this session). A sensible weekend path is courses (API fundamentals → tool use), then the cookbook notebooks on caching, JSON and RAG, then optionally the first chapters of LLMs-from-scratch. Throughout, **prefer current platform docs over any notebook dated before 2026**, especially for sampling and thinking parameters. Star counts and last-push dates for these repos could not be collected.

## Conclusion

Taken together, the sources show that much of the "agentic" and "advanced RAG" story is really about **budget allocation**. Multi-agent gains largely track token spend (80% of BrowseComp variance). Long context beats RAG when you can afford it, and Self-Route-style routing keeps most of that quality at a third to two-thirds of the cost. The graph-RAG wins are LLM-judged preference rates on summarisation tasks, not accuracy. So the useful question is not "which architecture?" but **"where should the next thousand tokens go, and can I show the judge that they worked?"** Answer that with a golden set and a trace, and the architecture usually follows: a cached long prompt or a hybrid retriever, a fixed pipeline, and at most one orchestrator fanning out to a few read-only specialists.

The second shift is in the ecosystem, and it is moving faster than tutorials can keep up. Within a year, GraphRAG froze, Verba was archived, AutoGen went into maintenance mode, AG2 dropped its `autogen` import, LangChain stopped recommending its own supervisor library, LangGraph's default step cap rose to 10,007, and current Claude models began rejecting `temperature`. For a hackathon team, the practical risk is not choosing the wrong pattern. It is copying a 2024 tutorial that no longer runs or no longer protects you. Pin versions, set every cap explicitly, check dates on everything, and treat any vendor or self-reported number in this report as a hypothesis to test on your own data.
